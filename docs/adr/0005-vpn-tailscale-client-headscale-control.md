# ADR-0005 · Private access layer: unmodified Tailscale clients, self-hosted Headscale, Go glue daemon

- **Status:** Agreed direction; implemented in `vpn/` and `deploy/vpn` with unit tests, Docker integration tests and a repeatable isolation probe, not yet validated against a production Headscale
- **Date:** 2026-10-27

## Context

Organisation members must reach their own Local AI host (Agent24 / iDoris) from any network without exposing it on the public internet. Tailscale's client is ubiquitous, free, and well maintained on every platform we care about, but its control plane is a SaaS operated by Tailscale Inc. Headscale is the mature (v0.29.x, BSD-3) open-source implementation of that control plane, feature-complete for our needs (pre-auth keys, ACL policy, MagicDNS, embedded DERP relay, OIDC, REST/gRPC API). Members should not have to configure anything; a background process should make the machine join the right network and keep it there.

## Decision

1. **Clients stay official.** Members install the stock Tailscale client. We do not fork, patch or redistribute it. On macOS/Linux a small daemon drives it through LocalAPI, exactly as the `tailscale login` CLI does. Mobile clients use Headscale's built-in onboarding pages or OIDC.
2. **Control plane is unmodified Headscale.** We run the upstream container with our configuration and ACL policy, plus Headplane (MIT) as admin UI. No fork of either; if we need a behaviour change we contribute upstream.
3. **Our code is glue only.** Two small Go programs: `idoris-vpn-enroll` (operator side, the only holder of a Headscale API key, issues single-use 10-minute pre-auth keys against per-tenant tokens) and `idoris-vpnd` (client side, reconciles tailscaled onto our control URL, re-enrolls on expiry, exposes a local status API, installs itself as launchd/systemd service).
4. **Single organisation by default; one Headscale user plus one dedicated tag per organisation, with per-organisation ACL rules.** The default deployment serves one organisation (`bootstrap.sh init`); adding a second one (`add-tenant`) is an explicit, advanced step. A tenant's members are the personal nodes of user `<tenant>@`. Its Local AI host is tagged `tag:<tenant>-local-ai`. The policy grants `<tenant>@` access to that tag on the iDoris/Agent24 ports only. It grants no member-to-member and no cross-tenant access. Headscale users are *not* a network isolation boundary: `autogroup:member` and tags are instance-wide, and v0.29.6 has no `autogroup:admin`. Instance-wide wildcards are therefore forbidden in the template. A local test showed that such a wildcard let one tenant's members reach another tenant's Local AI. Organisations that need stronger isolation get their own `deploy/vpn` instance.
5. **Go for this component.** The rest of the Bridge is planned in Rust, but the entire Tailscale/Headscale ecosystem is Go: `tailscale.com/client/local` is the supported LocalAPI client and the only way to mirror `tailscale login` semantics (profile switching, `Start` with auth key) without re-implementing the LocalAPI protocol. The module lives in its own `vpn/` directory with its own `go.mod`; it exposes nothing to the Rust crates except the local HTTP status API.
6. **Never take over a member's existing Tailscale login by default.** `takeover` defaults to false. The daemon has three modes (`auto` default, `system`, `embedded`). `auto` drives the system client only when that cannot displace someone else's login, and otherwise runs an in-process `tsnet` node with its own state directory next to it (no TUN, no system DNS; local access through loopback port forwards and SOCKS5). Switching the system client requires an explicit `takeover: true`. Mobile platforms allow one VPN at a time, so they cannot coexist.
7. **Operations are scripted, not hand-edited.** `bootstrap.sh` renders each organisation's policy block between marker comments, validates it with `headscale policy check` against the running server and reloads. Admin devices enroll exactly like members. The admin UI (Headplane) listens on loopback by default and can be restricted to the VPN itself. A subnet-router gateway is supported on Linux for devices that cannot run Tailscale; routes are approved manually or through `autoApprovers`.
8. **Release gates for licenses.** The shipped binaries are checked against an allowlist (Apache-2.0, BSD-2/3-Clause, MIT, ISC) in CI, and `THIRD_PARTY_NOTICES.md` is generated and kept in sync.

## Consequences

- Zero client maintenance burden; we inherit Tailscale's NAT traversal, key rotation, platform support and security updates.
- Tenant isolation on a shared instance is only as good as the policy file. Adding a tenant means adding its rule block, and a wrong rule can leak across tenants. Production Headscale must be reachable at https on port 443, because the Tailscale client forces TLS on 443 for re-dials.
- Headscale is single-instance by design; acceptable for small/medium organisations, requires a documented backup/upgrade routine (sqlite, noise key, DERP key).
- The Headscale API key is a crown jewel and is confined to the enrollment service container; clients only ever see single-use short-lived keys and a hashed tenant token.
- Members who already use Tailscale elsewhere are not disturbed: the embedded `tsnet` node coexists with their system client on macOS, Windows and Linux. The price is no system-level routing or MagicDNS for that node; applications reach the Local AI through `127.0.0.1` forwards or SOCKS5.
- Licensing: Headscale and Tailscale are BSD-3-Clause, Headplane MIT, all compatible with this repository's Apache-2.0. The transitive dependencies of the shipped binaries were scanned (42 modules, all permissive) and are guarded by `make licenses`. GPL-3.0 UIs (headscale-admin) may be deployed but not vendored. Publishing a built container image needs a different base than Alpine (GPL/MPL packages), see doc 12 section 10. Product naming must not imply endorsement by Tailscale or Headscale.
